1Executive Summary

What this is. A personal gaming backlog tracker for the creator and a small circle of friends (per PRODUCT.md): search RAWG, save games to a library with status/rating/playtime/notes, sort and reorder the backlog, view release calendars, ARPG events, and PC feature metadata (Steam, PCGamingWiki, Game Pass). Android via EAS/Play Internal Sharing; web export exists but public Vercel deployment is intentionally disabled.

Current maturity. Healthier than most side projects: TypeScript strict passes, lint is clean, 48 unit tests pass, secrets hygiene is good (nothing leaked in git history), RLS is enabled on every table, and the codebase follows its own AGENTS.md conventions closely. The core library workflow (search → add → track → reorder) is feature-complete on Android. The web build has real functional breaks, and a large dead subsystem (news pipeline) is still deployed.

Biggest risk. Two structural security decisions in the database: (1) a blanket grant migration gives anon and authenticated INSERT/UPDATE/DELETE on all current and future public tables, so one forgotten ENABLE ROW LEVEL SECURITY line on any future table means public write access; (2) two shared cache tables (game_external_ids, pcgamingwiki_features) are already writable by any authenticated user — one account can poison Steam/PCGW data for everyone. Exposure is small today (invite-only user base) but both are cheap to fix now and expensive to fix after an incident.

Best next move. Delete the dead news subsystem (ARCH-001) and land the Phase-1 correctness fixes. The news pipeline — 6 tables, 2 edge functions, ~2,000 lines, most of the backend's confirmed bugs — has had zero consumers since 20260619000002 unscheduled its cron jobs and the app's news routes became redirect stubs. Deleting it removes roughly half of this report's backend findings at once and shrinks the maintained surface dramatically.

Highest-leverage recommendations

  1. Delete the dead news subsystem (ARCH-001) — removes ~2,000 lines of buggy, unmonitored, deployed code and 6 frozen tables in one PR.
  2. Fix the RAWG per-entry fan-out + persist the query cache (PERF-001, BUG-006) — the library grid fires one RAWG /games/{id} call per entry on every cold launch; this pattern already burned 542k calls/month once (documented in migration 20260606000001).
  3. Make the web build actually work (BUG-002, UX-002) — Alert.alert is a silent no-op on react-native-web, so sign-out is impossible and every auth error is invisible on web. One small platform wrapper fixes five screens.
  4. Tighten DB grants and shared-cache RLS (SEC-001, SEC-002) — two short migrations close the standing footguns.
  5. Add CI (TEST-001) — typecheck, lint, and both test suites already exist and pass; they are enforced nowhere. A 40-line GitHub Actions workflow makes every other fix in this report durable.

SEC-001Shared cache tables are writable (and deletable) by any authenticated user SecurityHighConfidence: HighEffort: M
Evidence
supabase/migrations/20260520000001_add_game_external_ids.sql:13-16 — policy "Authenticated users can manage game external ids" is FOR ALL USING (auth.uid() IS NOT NULL). Same pattern on pcgamingwiki_features in 20260607172155_add_pcgamingwiki_ultrawide_cache.sql:29-32. Both tables are global (no user_id column) and read by every user.
Why it matters
Any single account can UPDATE or DELETE the rawg→steam mapping and the PCGW feature cache for all users — cache poisoning (wrong Steam links, wrong "Game Pass / ultrawide / 4K" flags) or wholesale deletion. Exposure is limited today (invite-only user base) but the design silently becomes dangerous the moment sign-ups open.
Recommended fix
Clients legitimately populate these caches (via useSteam.ts / usePcGamingWiki.ts), so don't remove write access blindly. Minimum viable hardening: drop DELETE, and replace free-form UPDATE with an "only fill or refresh" posture. Longer term, move cache writes server-side (the search-steam-app function already exists as the natural home for Steam-cache writes).
Execution plan
  1. Read mobile/hooks/useSteam.ts and mobile/hooks/usePcGamingWiki.ts to list exactly which columns the client inserts/updates on each table (so the new policies don't break the app).
  2. Create migration supabase/migrations/<timestamp>_tighten_shared_cache_policies.sql.
  3. For each of game_external_ids and pcgamingwiki_features: DROP POLICY the "…can manage…" FOR ALL policy; create separate FOR INSERT WITH CHECK (auth.uid() IS NOT NULL) and FOR UPDATE USING (auth.uid() IS NOT NULL) WITH CHECK (auth.uid() IS NOT NULL) policies; create no DELETE policy.
  4. Also REVOKE DELETE ON game_external_ids, pcgamingwiki_features FROM authenticated; (belt and suspenders at the grant layer).
  5. Verify with local stack: pnpm run db:reset, then exercise add-game → Steam lookup → PCGW features in the app against local Supabase.
  6. Do NOT push the migration to production — repo rule requires owner approval (AGENTS.md "Never push migrations… without asking").
Files likely touched
New file in supabase/migrations/ only. No app code changes if step 1 confirms the client never deletes rows (audit found no client-side .delete() on these tables).
Tests
Manual RLS check via SQL: as an authenticated role, attempt DELETE FROM game_external_ids — expect permission denied; INSERT/UPDATE still succeed.
Verification
pnpm run db:reset replays cleanly; app flows (Steam lookup, PCGW section on game detail) still populate caches locally.
Rollback risk
Low — policies are additive/restrictive; a follow-up migration can restore the old policy verbatim.
Dependencies
Local Supabase stack (Docker). Owner must apply to production.
SEC-002Blanket grants + default privileges give anon/authenticated write access to every current and future table SecurityHighConfidence: HighEffort: S
Evidence
supabase/migrations/20260513000002_grant_public_schema_privileges.sql:8-11 — GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO anon, authenticated; plus ALTER DEFAULT PRIVILEGES … GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO anon, authenticated;. (Added for the May 2026 PostgREST change that stopped default public-schema grants.)
Why it matters
Safety now rests 100% on never forgetting ENABLE ROW LEVEL SECURITY on any future table — one missed line = public read/write/delete, including for unauthenticated anon. DELETE for anon has no use case anywhere in the app. This is a standing footgun, not an active breach (audit confirmed all current tables do have RLS enabled).
Recommended fix
Narrow the default: anon gets SELECT only; authenticated keeps SELECT/INSERT/UPDATE (drop DELETE from the default privileges — grant DELETE explicitly per table that needs it, currently only library_entries and user_preferences).
Execution plan
  1. Create migration <timestamp>_narrow_public_grants.sql.
  2. REVOKE INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public FROM anon;
  3. REVOKE DELETE ON ALL TABLES IN SCHEMA public FROM authenticated; then GRANT DELETE ON library_entries, user_preferences TO authenticated;
  4. Replace both ALTER DEFAULT PRIVILEGES statements: future tables → SELECT to anon, SELECT, INSERT, UPDATE to authenticated.
  5. Grep the app for any other authenticated .delete() calls before finalizing step 3: grep -rn "\.delete()" mobile/hooks mobile/lib (audit found deletes only on library_entries).
  6. pnpm run db:reset and run the app against local: sign in, add/update/delete a library entry, edit prefs, edit display name.
Files likely touched
New migration only.
Tests
SQL probe as anon: INSERT into profiles → expect permission denied at the grant layer (before RLS even evaluates).
Verification
Full app smoke on local stack; pnpm run db:reset replays with no errors.
Rollback risk
Low-medium — if a grant is missed for a real flow, symptom is an explicit Postgres permission error (loud, easy to trace); revert = re-grant.
Dependencies
Best landed together with SEC-001 in one review. Owner applies to production.
